## Why JSON-LD?

### The Problem

ORP documents in YAML are excellent for humans:
- ✅ Readable, editable, version-controllable
- ✅ Validated by JSON Schema
- ✅ Portable (single file)

But they have limitations:
- ❌ **Not queryable across documents** - Can't ask "Show all datasets funded by pharmaceutical companies"
- ❌ **Not linked to existing ontologies** - Can't integrate with PROV, DCAT, Dublin Core ecosystems
- ❌ **Not interoperable** - Requires custom parsers, not compatible with semantic web tools

### The Solution: JSON-LD

**JSON-LD** (JSON for Linking Data) adds semantic meaning to JSON documents using RDF:

```json
{
  "@context": "https://openreason.org/context/v0.1",
  "@type": "Document",
  "title": "Danish Property Tax Reform",
  "authors": [{"name": "Asbjørn"}]
}
```

This becomes RDF triples:

```turtle
<orp-dk-property-tax-001> a orp:Document ;
    dc:title "Danish Property Tax Reform" ;
    dc:creator [ schema:name "Asbjørn" ] .
```

### What This Enables

1. **Cross-document queries**: "Find all stakeholders with representation='None'"
2. **Knowledge graphs**: Link ORP documents to PROV provenance chains, DCAT catalogs
3. **Semantic web tools**: SPARQL endpoints, RDF graph databases, visualization tools
4. **Ecosystem integration**: Compatible with W3C standards, Linked Open Data
5. **Forkable reasoning**: Track relationships between documents as RDF graph

## ORP Vocabulary Overview

ORP defines a **lightweight vocabulary** for concepts not covered by existing ontologies.

**Namespace:** `https://openreason.org/vocab/`
**Prefix:** `orp`
**Version:** 0.1

### Core Classes

| Class | Subclass of | Description |
|-------|-------------|-------------|
| `orp:Document` | `prov:Entity` | An ORP document |
| `orp:Dataset` | `dcat:Dataset`, `prov:Entity` | Dataset in Layer 1 |
| `orp:Stakeholder` | `schema:Person` | Affected stakeholder (Layer 3) |
| `orp:Decision` | `prov:Activity` | Methodological decision (Layer 4) |
| `orp:Fork` | `orp:Document` | Alternative/derivative document (Layer 5) |

### Core Properties

| Property | Domain | Range | Description |
|----------|--------|-------|-------------|
| `orp:complianceLevel` | Document | Literal | "basic", "standard", "full", "posthoc" |
| `orp:orpVersion` | Document | Literal | "0.1", "0.2", etc. |
| `orp:hasLayer1` | Document | DataProvenance | Link to Layer 1 content |
| `orp:exclusionCriterion` | Dataset | Exclusion | What was excluded |
| `orp:representation` | Stakeholder | Literal | "None", "Low", "Medium", "High" |
| `orp:forkType` | Fork | Literal | "critique", "alternative", "amendment", "response" |

**Full vocabulary**: See [`orp-vocabulary.md`](./orp-vocabulary.md)

## Reused Ontologies

ORP builds on established W3C and community standards to maximize interoperability.

### 1. Dublin Core (Metadata)

**Namespace:** `http://purl.org/dc/terms/`
**Prefix:** `dc`

| ORP Field | Dublin Core Term | Usage |
|-----------|------------------|-------|
| `title` | `dc:title` | Document/dataset titles |
| `summary` | `dc:description` | Descriptions |
| `authors` | `dc:creator` | Document authors |
| `created` | `dc:created` | Creation date |
| `last_updated` | `dc:modified` | Modification date |
| `domain` | `dc:subject` | Policy domain |
| `license` | `dc:rights` | License URL |

**Example:**
```json
{
  "title": "Danish Property Tax Reform",
  "created": "2024-01-10"
}
```

Becomes:
```turtle
:doc dc:title "Danish Property Tax Reform" ;
     dc:created "2024-01-10"^^xsd:date .
```

### 2. PROV-O (Provenance)

**Namespace:** `http://www.w3.org/ns/prov#`
**Prefix:** `prov`

| ORP Concept | PROV-O Term | Usage |
|-------------|-------------|-------|
| Document | `prov:Entity` | ORP documents are entities |
| Dataset | `prov:Entity` | Datasets are entities |
| Decision (L4) | `prov:Activity` | Decisions are activities |
| Author | `prov:Agent` | Authors are agents |
| Fork relationship | `prov:wasDerivedFrom` | Links forks to parents |
| Dataset creation | `prov:wasGeneratedBy` | Dataset generated by activity |
| Attribution | `prov:wasAttributedTo` | Dataset attributed to steward |

**Example:**
```json
{
  "@type": "Fork",
  "parent_document": "orp-dk-property-tax-001",
  "fork_type": "alternative"
}
```

Becomes:
```turtle
:alternative-001 a orp:Fork ;
    prov:wasDerivedFrom :orp-dk-property-tax-001 ;
    orp:forkType "alternative" .
```

### 3. DCAT (Data Catalog)

**Namespace:** `http://www.w3.org/ns/dcat#`
**Prefix:** `dcat`

| ORP Field (L1) | DCAT Term | Usage |
|----------------|-----------|-------|
| Dataset | `dcat:Dataset` | Layer 1 datasets |
| `source_url` | `dcat:landingPage` | Dataset homepage |
| `temporal_coverage` | `dcat:temporalCoverage` | Time period covered |
| `spatial_coverage` | `dcat:spatialCoverage` | Geographic coverage |
| `format` | `dcat:mediaType` | File format (CSV, Parquet, etc.) |

**Example:**
```json
{
  "temporal_coverage": {
    "start": "2023-01-01",
    "end": "2023-12-31"
  }
}
```

Becomes:
```turtle
:dataset dcat:temporalCoverage [
    dcat:startDate "2023-01-01"^^xsd:date ;
    dcat:endDate "2023-12-31"^^xsd:date
] .
```

### 4. Schema.org (People & Organizations)

**Namespace:** `http://schema.org/`
**Prefix:** `schema`

| ORP Field | Schema.org Term | Usage |
|-----------|-----------------|-------|
| Author name | `schema:name` | Person/org names |
| Affiliation | `schema:affiliation` | Institutional affiliation |
| Email | `schema:email` | Contact information |
| Funding source | `schema:funder` | (Alternative to orp:fundingSource) |

**Example:**
```json
{
  "authors": [{
    "name": "Asbjørn",
    "affiliation": "Public Reason Project",
    "email": "asbjorn@example.com"
  }]
}
```

Becomes:
```turtle
:doc dc:creator [
    a schema:Person ;
    schema:name "Asbjørn" ;
    schema:affiliation :public-reason-project ;
    schema:email "asbjorn@example.com"
] .
```

## Using the Context File

The ORP JSON-LD context file maps YAML field names to RDF URIs.

### Accessing the Context

**Published URL:** `https://openreason.org/context/v0.1`
**Local file:** [`orp-context.jsonld`](./orp-context.jsonld)

### Basic Usage

**Option 1: Reference by URL**
```json
{
  "@context": "https://openreason.org/context/v0.1",
  "document_id": "my-doc-001",
  "title": "My Policy Proposal"
}
```

**Option 2: Inline Context**
```json
{
  "@context": {
    "orp": "https://openreason.org/vocab/",
    "dc": "http://purl.org/dc/terms/",
    "title": "dc:title",
    "document_id": "@id"
  },
  "document_id": "my-doc-001",
  "title": "My Policy Proposal"
}
```

**Option 3: Embedded Context**
```json
{
  "@context": [
    "https://openreason.org/context/v0.1",
    {
      "custom": "http://example.org/custom#"
    }
  ]
}
```

### Context Structure

The ORP context defines:

1. **Namespace prefixes**
```json
{
  "orp": "https://openreason.org/vocab/",
  "prov": "http://www.w3.org/ns/prov#",
  "dcat": "http://www.w3.org/ns/dcat#",
  "dc": "http://purl.org/dc/terms/",
  "schema": "http://schema.org/"
}
```

2. **Field mappings**
```json
{
  "title": "dc:title",
  "created": {
    "@id": "dc:created",
    "@type": "xsd:date"
  }
}
```

3. **Type coercions**
```json
{
  "created": {
    "@id": "dc:created",
    "@type": "xsd:date"  // Ensures dates are typed correctly
  }
}
```

4. **Nested contexts** (for complex objects)
```json
{
  "authors": {
    "@id": "dc:creator",
    "@container": "@set",
    "@context": {
      "name": "schema:name",
      "role": "orp:role"
    }
  }
}
```

## Converting YAML to JSON-LD

### Manual Conversion

**Step 1: Start with YAML**
```yaml
orp_version: '0.1'
document_id: my-doc-001
title: My Policy Proposal
authors:
  - name: Alice
    role: author
```

**Step 2: Convert to JSON**
```json
{
  "orp_version": "0.1",
  "document_id": "my-doc-001",
  "title": "My Policy Proposal",
  "authors": [
    {"name": "Alice", "role": "author"}
  ]
}
```

**Step 3: Add JSON-LD context**
```json
{
  "@context": "https://openreason.org/context/v0.1",
  "@type": "Document",
  "orp_version": "0.1",
  "document_id": "my-doc-001",
  "title": "My Policy Proposal",
  "authors": [
    {"name": "Alice", "role": "author"}
  ]
}
```

**Step 4: Validate**

Use JSON-LD Playground: https://json-ld.org/playground/

Paste your JSON-LD → Click "Expand" → Verify RDF output

### Automated Conversion (Future)

```bash
# Future CLI feature (not yet implemented)
orp validate my-doc.yaml --format jsonld > my-doc.jsonld
```

**Current status:** Manual conversion only. CLI support planned for Sprint 1.8.x.

### Example: Full Document Conversion

See [`danish_property_tax_reform.jsonld`](../../examples/danish_property_tax_reform.jsonld) for complete example with all 5 layers.

## Querying with SPARQL

### Setting Up a Triple Store

**Step 1: Install triple store**

**Option A: Apache Jena Fuseki (Recommended)**
```bash
# Download from https://jena.apache.org/download/
wget https://dlcdn.apache.org/jena/binaries/apache-jena-fuseki-4.10.0.tar.gz
tar xzf apache-jena-fuseki-4.10.0.tar.gz
cd apache-jena-fuseki-4.10.0

# Start server
./fuseki-server --mem /orp
```

**Option B: GraphDB Free** (GUI-based)
Download from: https://graphdb.ontotext.com/

**Step 2: Load JSON-LD documents**
```bash
# Using Fuseki
curl -X POST -H "Content-Type: application/ld+json" \
  --data-binary @danish_property_tax_reform.jsonld \
  http://localhost:3030/orp/data

# Or use Fuseki web UI at http://localhost:3030
```

**Step 3: Run SPARQL queries**

Visit: http://localhost:3030/orp/sparql

Or use command line:
```bash
curl -X POST http://localhost:3030/orp/sparql \
  -H "Content-Type: application/sparql-query" \
  --data-binary @query.sparql
```

### Example Queries

**Query 1: Find all documents**
```sparql
PREFIX orp: <https://openreason.org/vocab/>
PREFIX dc: <http://purl.org/dc/terms/>

SELECT ?doc ?title ?compliance
WHERE {
  ?doc a orp:Document ;
       dc:title ?title ;
       orp:complianceLevel ?compliance .
}
```

**Query 2: Find stakeholders with no representation**
```sparql
PREFIX orp: <https://openreason.org/vocab/>
PREFIX schema: <http://schema.org/>

SELECT ?doc ?stakeholder ?name ?population
WHERE {
  ?doc orp:hasLayer3 ?l3 .
  ?l3 orp:stakeholder ?stakeholder .
  ?stakeholder schema:name ?name ;
               orp:representation "None" ;
               orp:estimatedPopulation ?population .
}
ORDER BY DESC(?population)
```

**More examples:** See [`sparql_examples.md`](./sparql_examples.md) for 15+ queries

### Programmatic Querying

**Python (RDFLib)**
```python
from rdflib import Graph

# Load JSON-LD
g = Graph()
g.parse("danish_property_tax_reform.jsonld", format="json-ld")

# Run SPARQL query
query = """
PREFIX orp: <https://openreason.org/vocab/>
PREFIX dc: <http://purl.org/dc/terms/>

SELECT ?title WHERE {
  ?doc a orp:Document ;
       dc:title ?title .
}
"""

for row in g.query(query):
    print(row.title)
```

**JavaScript (N3.js)**
```javascript
const N3 = require('n3');
const jsonld = require('jsonld');

// Convert JSON-LD to N-Quads
const doc = await jsonld.toRDF(jsonLdDoc);

// Load into N3 store
const store = new N3.Store();
const parser = new N3.Parser();
parser.parse(doc, (error, quad) => {
  if (quad) store.addQuad(quad);
});

// Query
const quads = store.getQuads(null, 'http://purl.org/dc/terms/title', null);
```

**Desktop Tools:**

2. **Cytoscape** (with RDF plugin)
   - Download: https://cytoscape.org/
   - Install RDF plugin
   - Visualize fork networks

### Fork Network Visualization

Use SPARQL CONSTRUCT to generate fork graph:

```sparql
PREFIX orp: <https://openreason.org/vocab/>
PREFIX prov: <http://www.w3.org/ns/prov#>
PREFIX dc: <http://purl.org/dc/terms/>

CONSTRUCT {
  ?fork prov:wasDerivedFrom ?parent .
  ?fork dc:title ?forkTitle .
  ?parent dc:title ?parentTitle .
}
WHERE {
  ?fork a orp:Fork ;
        prov:wasDerivedFrom ?parent ;
        dc:title ?forkTitle .
  ?parent dc:title ?parentTitle .
}
```

Export as Turtle, load into graph visualization tool.

## Integration Points

### 1. PROV-O Provenance Systems

ORP documents are `prov:Entity` instances, so they integrate seamlessly with PROV-O tools:

**Use case:** Track provenance chain from dataset → ORP document → policy decision

```turtle
# Dataset
:danish-valuations a prov:Entity, dcat:Dataset ;
    prov:wasGeneratedBy :valuation-activity ;
    prov:wasAttributedTo :danish-tax-authority .

# ORP Document
:dk-tax-reform a prov:Entity, orp:Document ;
    prov:used :danish-valuations ;
    prov:wasGeneratedBy :policy-analysis .

# Policy Decision
:tax-law-2024 a prov:Entity ;
    prov:wasDerivedFrom :dk-tax-reform .
```

**Tools:**
- [ProvStore](https://provenance.ecs.soton.ac.uk/store/) - PROV repository
- [PROV Toolbox](https://lucmoreau.github.io/ProvToolbox/) - PROV validators

### 2. DCAT Data Catalogs

Layer 1 datasets can be published to DCAT catalogs:

**Example: European Data Portal**
```turtle
:catalog a dcat:Catalog ;
    dc:title "ORP Datasets Catalog" ;
    dcat:dataset :danish-valuations .

:danish-valuations a dcat:Dataset, orp:Dataset ;
    dc:title "Danish Property Valuations 2023" ;
    dcat:distribution [
        dcat:downloadURL <https://data.skat.dk/valuations.csv> ;
        dcat:mediaType "text/csv"
    ] .
```

**Tools:**
- [CKAN](https://ckan.org/) - Open data portal (DCAT-compatible)
- [DataCite](https://datacite.org/) - Dataset DOI minting

### 3. Linked Open Data (LOD) Cloud

Publish ORP documents as Linked Data:

**Requirements:**
1. Dereferenceable URIs (e.g., `https://openreason.org/docs/dk-tax-reform-001`)
2. Content negotiation (serve HTML for browsers, RDF for semantic agents)
3. Backlinks to related datasets/documents

**Example:**
```bash
# Browser request
curl -H "Accept: text/html" https://openreason.org/docs/dk-tax-reform-001
# Returns: HTML page

# RDF client request
curl -H "Accept: application/ld+json" https://openreason.org/docs/dk-tax-reform-001
# Returns: JSON-LD document
```

### 4. W3C Solid Pods

Store personal ORP documents in Solid pods:

```javascript
// Store ORP document in Solid pod
const { overwriteFile } = require('@inrupt/solid-client');

await overwriteFile(
  'https://mypod.solidcommunity.net/orp/my-doc.jsonld',
  new Blob([jsonLdContent], { type: 'application/ld+json' }),
  { fetch: session.fetch }
);
```

## Best Practices

### 1. Use Stable URIs for Documents

**Good:**
```json
{
  "document_id": "orp-dk-property-tax-001"
}
```

Maps to: `https://openreason.org/docs/orp-dk-property-tax-001`

**Bad:**
```json
{
  "document_id": "my-doc"  // Too generic
}
```

**Best practice:** Use domain + short descriptive ID + version

### 2. Always Include @type

```json
{
  "@context": "https://openreason.org/context/v0.1",
  "@type": "Document",  // ← Always specify type
  "document_id": "...",
  "title": "..."
}
```

Enables type-based queries: `SELECT * WHERE { ?x a orp:Document }`

### 3. Use Blank Nodes for Nested Objects

```json
{
  "net_welfare_impact": {
    "direction": "negative",
    "magnitude": "moderate",
    "confidence": "high"
  }
}
```

Becomes anonymous blank node:
```turtle
:stakeholder orp:netWelfareImpact [
    orp:direction "negative" ;
    orp:magnitude "moderate" ;
    orp:confidence "high"
] .
```

**Alternative:** Use named URIs for important nested objects

### 4. Validate Before Publishing

```bash
# Validate with JSON-LD Playground
# https://json-ld.org/playground/

# Or use RDFLib
python -c "
from rdflib import Graph
g = Graph()
g.parse('my-doc.jsonld', format='json-ld')
print(f'Loaded {len(g)} triples')
"
```

### 5. Version Your Context

**Bad:**
```json
{
  "@context": "https://openreason.org/context/latest"
}
```

**Good:**
```json
{
  "@context": "https://openreason.org/context/v0.1"
}
```

Ensures stability - v0.1 context never changes.

### 6. Document Custom Extensions

If extending ORP vocabulary:
```json
{
  "@context": [
    "https://openreason.org/context/v0.1",
    {
      "myext": "https://myorg.org/orp-extension#",
      "customField": "myext:customField"
    }
  ]
}
```

Publish extension schema at `https://myorg.org/orp-extension`

## Troubleshooting

### Issue 1: Context Not Found (404)

**Error:**
```
Error loading context: https://openreason.org/context/v0.1
```

**Solution:**
- Use local copy of `orp-context.jsonld`
- Or wait for official publication of context file
- Temporary: Use inline context

### Issue 2: Type Coercion Errors

**Error:**
```
Expected xsd:date but got string "2024-01-10"
```

**Solution:**
Ensure dates use proper format:
```json
{
  "created": "2024-01-10"  // ISO 8601 format
}
```

Context automatically types as `xsd:date`.

### Issue 3: Blank Node Labels Not Preserved

**Problem:** Blank nodes get random IDs when loaded

**Solution:** This is expected RDF behavior. Use named URIs for important entities:
```json
{
  "stakeholder_id": "stakeholder-homeowners-001"
}
```

### Issue 4: Large Documents (>10MB)

**Problem:** JSON-LD processors may timeout

**Solution:**
- Split into multiple documents (link via `dc:relation`)
- Use streaming RDF parser (RDFLib)
- Increase processor memory limit

### Issue 5: Namespace Conflicts

**Error:**
```
Conflicting definitions for "name"
```

**Solution:**
Be explicit about namespaces:
```json
{
  "@context": {
    "dc_name": "dc:title",
    "schema_name": "schema:name"
  }
}
```
